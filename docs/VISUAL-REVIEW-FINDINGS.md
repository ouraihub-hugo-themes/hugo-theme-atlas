#td-i-rocket  cards-2  bboxW=15

42 个图标全部正常渲染，`href` 均为同文档的 `#td-i-*`，零个跳文件引用。

## 二、七处怀疑逐条结论

### 1. plain 档下的卡片边界 —— 本次无法判断

`#testimonials-19`（muted）的卡片浮起清楚，边界一眼可辨。

但**任务书真正要问的情形在这 22 节里不存在** —— 没有任何一节是卡片类落在
plain 档。`.td-landing-plan` 在 `#pricing-7`（muted），`.td-landing-quote` 在
`#testimonials-19`（muted）。要判断"1px 边框在同色底上够不够"，需要专门造一节
plain 档的卡片来看。

### 2. 条形图里 3.2% 那根条 —— 过

**能读作"一根很短的条"，不会读成"没渲染"。**

具体看到的：那 15px 是一个填满轨道高度的、两端圆角的深蓝色胶囊，颜色与上方
42 KB（约 210px）和下方 118 KB（约 580px）那两根完全一致。三根条左端对齐在同一
垂直线上，所以它读起来是「同一组里最短的那根」，而不是「空的」。右侧
`3.8 KB` 的数值标签也在，进一步排除了误读。

不需要加最小宽度。

### 3. capabilities 的 partial 档图标 —— 过（但依赖上下文）

三档实际渲染出来的形状：

| 状态 | 图标 | 视觉 |
| --- | --- | --- |
| `yes`（四种阅读外壳、打印样式） | `check` | 蓝色勾 ✓ |
| `partial`（32 种语言） | `angle-down` | 灰色向下尖角 ∨ |
| `no`（联网功能） | `close` | 灰色叉 ✕ |

**结论：在这个三者并列的语境里，向下尖角能读作“介于两者之间”。**

理由不是它本身像“部分”，而是三个形状构成了一组可区分的梯度：勾是完成、
叉是否定、尖角既不是勾也不是叉。加上颜色差异（勾是蓝色，后两者是灰色），
三档一眼能分开。

**两个保留意见：**

1. **脉冲不强。** 向下尖角单独看仍然更像“展开”（它在 FAQ 里就是这个含义）。
   现在能读对，靠的是旁边有 ✓ 和 ✕ 做对照。如果哪一页只有 partial 一种状态，
   读者拿不到那组梯度，就会误读。
2. **灰色把 partial 和 no 推到了同一档。** 两者颜色相同（`rgb(61,78,97)`），
   只靠形状区分；而 yes 另外有颜色加持。如果希望 partial 读起来“比 no 好”，
   现在的配色没体现这一层。

不需要换图标。如果要动，改颜色比换字形更直接。

**处置（2026-09-03）：换了，用户拍板 `minus`。** 上面那句「不需要换」是第一轮
在图标全站未渲染的前提下写的推理，不是看着图给的 —— 而它自己的保留意见 1 已经
说明了问题：向下尖角单独看像「展开」。用户看四种方案的对照图后选了减号。

这一条也顺带否掉了当时「图标库里没有减号」的说法：清单里本来 71 个，加
`minus` 后 72 个，那是没查清单就下的结论。保留意见 2（partial 与 no 同为灰色）
仍然成立，但 no 那档另有标题划线，不是只靠颜色 —— 见 `landing.css` 的
`data-td-status="no"` 一段。

### 4. logo 墙的灰度 + 半透明 —— 不过（两个问题）

- **灰度压得过重。** 0.7 的透明度本身不算太淡，但配合 `grayscale(1)` 之后，
  三个图呈现为从上到下的灰→深灰渐变色块，看不出任何轮廓或图形内容，就是三个
  素色矩形。不是"淡到看不清"，是"暗到读不出东西"。
- **三个 logo 整体偏右。** 具体位置：节宽 1568px（含 2× 缩放），三个图块大约从
  x=620 排到 x=945，即集中在页面右中部；而同一节的标题「构建工具」在 x=96。
  logo 组既没与标题左对齐，也没在节内真正居中，左侧空出一大片。这与 fixture
  用同一张图无关，是布局问题。

悬停恢复彩色的过渡：静态截图无法验证，**未测**。

---

#### 2026-09-03 的处置

**「偏右」是真的，「未真居中」不是。** 1280 视口下实测：三个 logo 落在 499–766，
中心 632.5；列表框 73–1193，中心 633。**精确居中**，`justify-content: center`
如实生效。真缺陷是同一节里两套对齐 —— 标题在 73（`text-align: start`），内容
居中。

改成 `justify-content: start`，跟着节标题。判据是全站惯例而不是审美：21 个
section 逐个量过标题块相对内容框的左右余量，**19 个左贴边（左 16 / 右 432），
只有 `command-box-10` 与 `cta-21` 两边余量相等**，而那两节的标题自身就是
`text-align: center`（整节居中的设计）。`logo-wall-20` 的标题是 `start`，所以
内容跟标题。改后实测标题与首个 logo 同在 x=73。

**灰度那条另有原因，也改了：撤掉 `opacity: 0.7`，只留 `grayscale(1)`。**
评审说"看不出任何轮廓或图形内容，就是三个素色矩形"——**这一半是 fixture 的
属性，不是滤镜的**：`make-fixture-image.js:53` 画的就是对角渐变加网格线，本身
没有任何 logo 形状，灰度化一张渐变图得到的必然是灰渐变矩形。

但两层压暗叠加确实过重，这一条独立成立。亮色底 `rgb(241,244,248)` 上按 WCAG
线性权重算合成后的对比度：

| 品牌色 | 只 grayscale | 再叠 opacity 0.7 |
| --- | --- | --- |
| 纯黑 | 19.04 | 8.15 |
| 深海军蓝 | 13.36 | 5.28 |
| Hugo 粉 | 4.00 | 2.46 |
| Tailwind 青 | 2.23 | 1.71 |
| esbuild 黄 | 1.49 | 1.31 |

`opacity` 砍掉 30–60%，而"让彩色 logo 退到背景里"这个目标 `grayscale` 一层已经
达到 —— 第二层买的不是层次，是让浅色字标糊进背景。WCAG 明文豁免 logotype 的
对比度要求，所以这不是合规问题，是能不能认出是哪一家。
print 与 forced-colors 两处的覆盖规则同步去掉了已经不存在的 `opacity: 1`。

### 5. 相邻同色节的分界 —— 不过

**8rem 的间距不够。** 以 `#hero-0` → `#metrics-1` 为例：两节背景色完全相同（亮色下
都是 `rgb(241,244,248)`），中间无分界线、无阴影、无宽度变化，唯一的分隔信号就是
一段空白。而节内部的元素间距（例如 hero 按钮组到下方图片）与这段节间空白在量级上
接近，所以读下来像是同一节里的下一段，而不是新的一节。

缓解因素：节标题字号足够大且是粗体（`一些数字` 目测 40px 以上，与正文层级差明显），
所以不至于让人迷路 —— 能看出「这里开始讲新东西」，但看不出「这是一个新的 section」。

**→ 已改（2026-09-03）：同档相邻处加一道 1px 线。**
不加留白 —— 这是量级问题不是数值问题，8rem 改 12rem 只是把页面拉长，读者仍分不出
「新段」与「新节」。选择器枚举三档（`--plain + --plain` 等）而不写 `:has()`：tone
是三值枚举且模板对每一档都发显式 class。实测 22 节里画出 6 道线，全部落在同档相邻
处，零漏零误。颜色走 `--color-border`，合成后对比度亮色 1.25 / 暗色 1.32 —— 是细线
而不是分隔条。`forced-colors` 下 UA 自动换系统前景色（实测纯黑），无需额外覆盖。

这 6 处里有 2 处（`case-study-18 → testimonials-19`、`testimonials-19 →
logo-wall-20`）是因为 `testimonials-19` 目前被临时改成 `tone: plain` 供评审看最坏
情形。改回 `muted` 之后剩 4 处，与本文档正文说的「四对」一致。

### 6. timeline 的竖线收尾 —— 过（本次最干净的一节）

- 线**正好收在第三个圆点上方**，没有多出的尾巴。第三条（「模糊时间」）圆点下方
  完全无线。
- 第二段与第三个圆点之间**没有断缝**，线段直接接到圆点边缘。
- 三种圆点**一眼能分**，且区分靠的是形状而不只是深浅：
  - done（`2026-01-15`）—— 实心深蓝圆点
  - current（`2026-06`）—— 白心 + 蓝色描边的空心圈
  - planned（`2027`）—— 淡灰实心圆点，明显比前两个淡

### 7. 暗色模式

- **`#cta-21` 的 accent 档 —— 偏亮。** 整节背景是一块饱和度较高的中蓝（目测接近
  `#8ab4d8` 那个亮度档），占整个节宽，在周围几乎全黑的页面里亮度跳得很多。
  标题「收尾那一块」与正文都是近黑色，字本身读起来殫无因难；问题不在对比度，
  而在从上一节（深色 `#logo-wall-20`）滚下来时的亮度突变。

  **→ 已改（2026-09-03），量化确认了这条判断。** 暗色下这一节与页面的亮度跳变
  实测 8.16，亮色下同一节是 6.06（亮色 accent 是深蓝铺浅底，方向相反）。原因是
  `--td-accent` 就是链接色，它在暗色下翻成 `#7db3e0`（L=0.42）本身对，但令牌注释
  写明它的用途是薄的 —— 14% 选中态、7% hover、1px 边框；铺满一节是另一个量级。
  85% 混 canvas 后跳变 6.02，与亮色对齐，标题与副标题实测都是 6.02，过 AA。
  用 `color-mix` 派生而不加新令牌：`theme_color` 只改两个值，派生式自动跟随；
  整幅 accent 底色全仓库只有这一处，另外四处（primary 按钮、timeline 圆点、
  徽章、条形填充）都是小面积，本来就该按原亮度跳出来 —— 实测按钮在暗色下仍是
  `(125,179,224)`，没被这条规则碰到。
- **`#pricing-7` featured 粗边框 —— 过。** 中间那张卡（「团队版 ¥299」）四周是一道
  浅蓝边框，在近黑卡面和深色节底上很清楚；旁边两张卡（「社区版」「企业版」）
  的边框是暗灰色，两者差异明显，一眼能看出中间那张被突出。比亮色模式下还明显。
  另外「最常选」徐章是浅蓝底 + 深色字，也清楚。
- **`#preview-15` 窗口外框三个圆点 —— 过，没有消失。** 在窗口标题栏左上角
  能看到三个横排的灰色小圆点，亮度比标题栏底色高一档，不抢眼但确实存在。

#### `#capabilities-17` 的处置：18rem → 16rem（2026-09-03）

先纠正描述：**三列宽度是相等的**，实测 `352px 352px 352px`，不是"按内容自然
宽度排"。不等的是**列内的内容宽度**：113 / 248 / 285 / 263 —— 第一项只填了它那
一列的 32%，看起来才散。

改的是 `minmax` 的最小值，而这个数字真正决定的是**note 跟标题同行还是换行**：
最宽一项的内容行内需要 295px（≈18.4rem），18rem 排出的 352px 列刚好够它不折行，
16rem 排出的 256px 列则让 note 落到标题下面。选换行 —— note 是标题的附注，
`.td-landing-capability` 本来就写了 `flex-wrap: wrap` 等这件事发生。列数因此不
再受"最长那条注解有多长"支配，而那本来是作者的文案长度，不该决定版面。

四个候选都量过（1120px 列表宽，横向 gap 32px）：

| min | 列数 | 行数 | 空格位 | 列表高 | 每项高 |
| --- | --- | --- | --- | --- | --- |
| 16rem | 4 | 1 | 0 | 55 | 55（note 换行） |
| 18rem（原） | 3 | 2 | 2 | 60 | 24（note 同行） |
| 18rem + `max-content` | 3 | 2 | 2 | 60 | 24（右侧收到 944） |
| `auto-fill` 18rem | 3 | 2 | 2 | 60 | 24（与 auto-fit 无差别） |

附带解掉了评审报的松散，但**没有哪个 min 能对所有条目数都排满**（16rem 下 5 项
同样空 1 格），所以填满格位是结果不是理由 —— 按条目数挑 min 就是在给 fixture
调版面。

#### `#metrics-1` 的处置：不改（2026-09-03）

先纠正描述：**基线是齐的。** 实测四个容器都是 97px 高、`top` 与 `bottom` 全等
（grid 拉伸），value 顶边四列都在 701、label 都在 749。参差的是**墨迹下沿** ——
第 2 项到 802，另外三项到 777，差 25px，就是那一行 note。

试过用 subgrid 修（列间共享行网格，让空的 note 行也占位）。**A/B 实测它买不到
东西**：

| | 容器下沿 | 墨迹（1/3/4 项） | 墨迹（第 2 项） |
| --- | --- | --- | --- |
| subgrid | 802 | 777 | 802 |
| 原 flex | 798 | 773 | 798 |

参差量一模一样（都 25px），而空的第三行照样吃掉一份 row gap，四列白白高 4px。
原因是 note 是最后一个子元素，它下面没有东西可以对齐 —— 行网格对"最后一行有没有
内容"无能为力。已撤回，理由记在 `landing.css` 的 `.td-landing-metric` 上。

不另找办法的理由：要让四列墨迹齐，只能给没写 note 的三项预留一行空白。那是**为了
让一项好看而给另外三项加不存在的内容**，而 note 是逐项可选字段 —— 作者只给其中
一个数字加一句注解是正常写法，主题照它写的排就是对的。fixture 故意只给第 2 项写
note，覆盖的正是"有/无"两种情况。

## 五、一个假象，不用查

**360 宽度下 `#pricing-7` 的截图里，导航栏压住了第一张卡的价格。**

这是逐节截图方法的产物 —— `scrollIntoViewIfNeeded()` 把元素滚到了 sticky
header 下面。`.td-navbar` 是 `position: sticky`、高 50px、`z-index: 100`，
正常滚动浏览不会出现这个遮挡。

（顺带：`#pricing-7` 的 `scroll-margin-top` 是 `0px`。锚点跳转会不会被 header
遮住是另一个问题，本次未验证。）

**2026-09-03 验掉了：不是缺陷，是量错了属性。** `scroll-margin-top` 为 0 说明
不了什么 —— 挡住遮挡的是滚动容器上的 `scroll-padding-top`，而
`base.css:6` 给 `html` 写的是 `calc(var(--td-shell-nav-h) + 1rem)`，实测
computed 值 66px，navbar 50px。这条在滚动容器上，所以对**所有**锚点一起生效，
不必逐个元素写 `scroll-margin`。

实测：landing 页 25 个 `section[id]` 逐个跳过去，等滚动稳定后量顶边与
navbar 底边（50px）的关系 —— **零个被遮挡**。`#pricing-7` 顶边落在 66px，
标题 130px。已滚到文档底部的节要排除，那种情况顶边在 navbar 上方是因为文档
不够长，不是遮挡。

## 六、复现方法

### 环境

```powershell
cd <主题仓库>
pnpm css:build; pnpm ts:build
hugo server --source exampleSite --themesDir ../.. --port 1319 --renderToMemory
```

### 两个坑

**1. 用 `127.0.0.1` 而不是 `localhost`。**
hugo 只绑 IPv4（`Get-NetTCPConnection -LocalPort 1319` 显示 `LocalAddress`
为 `127.0.0.1`）。`localhost` 在本机解析到 IPv6 `::1`，请求直接失败。
任务书里写的 `http://localhost:1319/landing/` **连不上**，
要用 `http://127.0.0.1:1319/landing/`。

**2. hugo 参数别经 `pwsh -Command` 传。**
`--themesDir ../..` 会被吞掉，hugo 打印一整屏帮助文本，真正的错误在最后一行。
写进 `.ps1` 脚本文件用 `-File` 执行，或直接调 exe。

### 浏览器

按任务书的 B 方案，不装任何包：

```js
process.env.PLAYWRIGHT_BROWSERS_PATH = '<浏览器缓存目录>';
const { chromium } = require(
  '<.../node_modules/playwright-core>'
);
const browser = await chromium.launch({
  executablePath:
    '<那个目录里的 chrome.exe>',
});
```

### 验证图标 bug 是否已修

```js
await page.evaluate(() =>
  [...document.querySelectorAll('svg.td-icon use')]
    .map((u) => u.getBBox().width)
    .filter((w) => w === 0).length
);
// 修好前：40   修好后应为：0
```
